## MODIFIED Requirements

### Requirement: PCA Feature Selection Config Validation

The system SHALL validate that `pca.n_top_features` is a whole number
`>= 1` (within a small floating-point tolerance, not exact equality)
whenever `pca.feature_selection_strategy` is one of `"top_absolute"` or
`"top_contribution"` — methods that read `n_top_features` directly as an
integer count and would silently truncate (to zero, or dropping a
fractional part) if given a value that isn't a positive whole number. The
same whole-number requirement applies to `"top_variance"` whenever
`n_top_features >= 1` (its count branch), but `"top_variance"`
additionally accepts any value `< 1` as a variance-fraction threshold. No
restriction is added for `feature_selection_strategy == "extreme"` (the
field is ignored entirely by this method, so any value is harmless).

Validation occurs in `validate_viz_config()` only, which runs at pipeline
startup before any steps execute. `QCPipelineConfig` has no `pca` field
(removed — see the "No PCA Field on QC Pipeline Configuration" requirement
below), so `validate_qc_config()` has nothing to validate here; this
requirement previously stated validation ran in both functions (also at
pipeline startup, before any steps execute), which was true only while
`QCPipelineConfig` still carried an unused `pca` field. `"vector_length"`
is intentionally not one of the
strategies this requirement names: `pca.feature_selection_strategy`'s own
pre-existing validation enum (in `validate_viz_config()`) has never
accepted `"vector_length"` as a value for this field — that string is a
valid value only for the separate
`create_pca_biplot(feature_selection=...)` parameter. This requirement
does not widen that enum.

#### Scenario: Reject a fractional n_top_features below 1 for count-only methods

- **WHEN** a viz config has `pca.feature_selection_strategy` set to
  `"top_absolute"` or `"top_contribution"` and `pca.n_top_features` set to
  a value `< 1`
- **THEN** `validate_viz_config()` SHALL raise a `ValueError` before any
  pipeline steps execute
- **AND** the error message SHALL name both config fields, the offending
  strategy, and state that an integer `>= 1` is required for that strategy

#### Scenario: Reject a non-integer n_top_features at or above 1

- **WHEN** a viz config has `pca.n_top_features` set to a non-integer
  value `>= 1` (e.g. `5.7`) and `pca.feature_selection_strategy` set to
  any value other than `"extreme"` (including `"top_variance"`,
  `"top_absolute"`, or `"top_contribution"`)
- **THEN** `validate_viz_config()` SHALL raise a `ValueError` before any
  pipeline steps execute
- **AND** the error message SHALL state that the fractional part would be
  silently truncated

#### Scenario: Accept a variance-fraction threshold for top_variance

- **WHEN** a viz config has `pca.feature_selection_strategy="top_variance"`
  and `pca.n_top_features` set to a value `< 1` (e.g. `0.8`)
- **THEN** `validate_viz_config()` SHALL pass without error

#### Scenario: Accept any n_top_features value for extreme

- **WHEN** a viz config has `pca.feature_selection_strategy="extreme"` and
  `pca.n_top_features` set to any value, including a fractional value or
  one `< 1`
- **THEN** `validate_viz_config()` SHALL pass without error, since the
  field is not read for this method

#### Scenario: Accept a whole-number count for any strategy

- **WHEN** a viz config has `pca.n_top_features` set to a whole-number
  value `>= 1`, regardless of `pca.feature_selection_strategy`
- **THEN** `validate_viz_config()` SHALL pass without error

#### Scenario: Default config values pass validation

- **WHEN** a `PCAConfig` is constructed with default values
  (`feature_selection_strategy="top_variance"`, `n_top_features=10.0`)
- **THEN** `validate_viz_config()` SHALL pass without error

#### Scenario: QC configs have no PCA feature-selection field to validate

- **GIVEN** a `QCPipelineConfig` (which has no `pca` field)
- **WHEN** `validate_qc_config()` runs
- **THEN** it SHALL NOT raise `AttributeError` and SHALL NOT perform any
  `pca.feature_selection_strategy`/`pca.n_top_features` validation, since
  there is no such field to read

## ADDED Requirements

### Requirement: No PCA Field on QC Pipeline Configuration

`QCPipelineConfig` SHALL NOT have a `pca` field. No step in `QCPipeline`'s
step list reads PCA configuration — `PCAAnalysisStep`,
`GenerateStaticFiguresStep`, and the PCA figure generated by
`generate_summary_viz.py` are wired only into `VizPipeline`, never into
`QCPipeline`. A `pca` field on `QCPipelineConfig` configures a value
nothing in a QC run reads. `VizPipelineConfig` is unaffected and keeps its
own `pca: PCAConfig` field, still read by the three viz-only steps above.

Every QC config YAML file SHALL NOT contain a top-level `pca:` key —
`load_qc_config()`'s strict `OmegaConf.merge(OmegaConf.structured(...), ...)`
raises `ConfigKeyError` at load time for any key absent from the target
dataclass, so a QC config with a leftover `pca:` block fails to load
entirely, not silently degrades.

#### Scenario: QCPipelineConfig has no pca attribute

- **WHEN** a `QCPipelineConfig` is constructed with any arguments
- **THEN** it SHALL NOT have a `pca` attribute

#### Scenario: A QC config YAML with a pca: block fails to load

- **GIVEN** a QC config YAML file containing a top-level `pca:` key
- **WHEN** `load_qc_config()` is called on that file
- **THEN** it SHALL raise `ConfigKeyError`, since `pca` is not a field of
  `QCPipelineConfig`

#### Scenario: Every committed QC config loads without a pca: block

- **GIVEN** the fixed, hardcoded list of 59 QC config files identified by
  the exhaustive repo-wide sweep for this change (committed under
  `configs/` — excluding `configs/archive/` and `configs/saved_backups/`,
  which are frozen historical snapshots not reloaded by any current
  tooling — and `tests/fixtures/harness/qc/`)
- **WHEN** each is loaded with `load_qc_config()`
- **THEN** none SHALL raise, since none contains a top-level `pca:` key
- **AND** this SHALL be enforced by a committed regression test asserting
  the hardcoded list, not a path/content heuristic that could silently
  drift from the set of files actually edited

#### Scenario: No QC step reads config.pca

- **GIVEN** `QCPipeline`'s full step list
- **WHEN** any step in that list executes
- **THEN** no step SHALL read a `config.pca` attribute — verified
  statically (no `config.pca` reference exists in any QC step's source)
  and dynamically (running `QCPipeline` end-to-end against an identical
  synthetic dataset with `pca.feature_selection_strategy`/`n_top_features`
  set to non-default values, prior to this field's removal, produces
  byte-identical output to a run with `pca` left at its defaults)
